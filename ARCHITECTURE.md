# ARCHITECTURE.md — the v2 technical spec

The design that lets ~71 tools share a theme, helpers, hub, CSP, and PWA layer **without giving up
the single-file, double-clickable contract**. Companion docs: [MIGRATION.md](MIGRATION.md) (how
tools get here), [API-AND-RELAY.md](API-AND-RELAY.md) (network policy), [QUALITY.md](QUALITY.md)
(gates the build enforces).

---

## 1. The single-file contract

Every file in `dist/` MUST:

- be fully self-contained — no `<script src>`, no `<link href>`, no external fonts/images except
  data-source URLs (API calls, map tiles, radar/satellite imagery);
- open and function from `file://` (double-click) with no server, for everything except
  http-only browser features (PWA install, clipboard/geolocation quirks already documented in v1);
- carry a generated header comment: `<!-- GENERATED by build.py — edit tools/<name>.html -->`;
- never be edited by hand (the build's staleness check enforces this, see §5).

## 2. Source / dist model

**Source tools are valid, runnable HTML.** During development you edit `tools/weather.html` and
open it directly — relative links resolve the shared core from `file://`, so there is **no build
step in the edit-refresh loop**. Build only to publish.

```html
<!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>Weather Station · Local Suite</title>
<link rel="stylesheet" href="../core/suite.css" data-suite-inline>
<style>
  /* tool-local: accent overrides, layout, components. Stays in this file. */
</style>
</head>
<body>
  <!-- tool markup; shared chrome (back-link, theme button) comes from core patterns -->
<script src="../core/suite.js" data-suite-inline></script>
<script>
"use strict";
/* tool logic — exactly as simple as v1, minus the ~60–90 duplicated lines */
</script>
</body>
</html>
```

`build.py` replaces every `data-suite-inline` tag with the referenced file's contents, producing
`dist/weather.html`: byte-for-byte self-contained. The hub uses one extra marker (§4.3).

**What lives where:**

| In `core/suite.css` | Stays per-tool |
|---|---|
| the 3-layer theme block (`:root` vars, `prefers-color-scheme`, `data-theme` overrides) — canonical copy is v1 `weather.html:8–70` | tool accent variables (`--data`, `--warm`, `--alert`, `--good`, …) |
| reset (`* { box-sizing: border-box; margin: 0 }`) + body font stack | all layout (`.wrap` width choices, grids, app shells) |
| shared chrome: `.back`, `.theme-btn`, `.card`, `.chip`, `.search`, `footer`, focus-visible styles, `prefers-reduced-motion` guard | tool-specific components |

## 3. `core/suite.js` — the `Suite` namespace

One IIFE defining a single global. Small, boring, dependency-free. The complete public API:

```js
Suite.theme.init()                 // reads suite.theme, sets documentElement.dataset.theme
Suite.theme.toggle()               // flips + persists; wired to the .theme-btn in shared chrome

Suite.fetchJSON(url, {timeout=12000, cacheKey, ttl, fallbackToCache=true})
  // AbortController timeout; on success writes {t: Date.now(), v: data} to
  // localStorage[`suite.cache.${cacheKey}`]; on failure returns stale cache (flagged
  // {stale: true, t}) so tools render the v1-style "Offline — cached from …" card.
  // Unifies v1's getJSON / fetchWithTimeout variants.

Suite.store.get(key, fallback)     // JSON parse with try/catch, suite.* namespace enforced
Suite.store.set(key, value)
Suite.store.migrate([...fns])      // ordered migrations, gated by suite.meta.schemaVersion (§6)

Suite.esc(str)                     // HTML-escape; mandatory for remote data in innerHTML (QUALITY.md)
Suite.liveRegion(el)               // marks an async result container aria-live="polite" (QUALITY.md)

Suite.location.get() / .set({lat, lon, label})   // the shared suite.location key
Suite.key(name)                    // reads suite.key.<name>; returns {value, isDemo} with
                                   // DEMO_KEY fallback where the API offers one
Suite.relay(url)                   // optional power-user hook: rewrites url through
                                   // localStorage suite.relay.url if set; null otherwise →
                                   // tool uses its link-out/embedded path (API-AND-RELAY.md §6)

// PWA (inert from file:// — see PWA.md):
// if (location.protocol.startsWith('http')) navigator.serviceWorker.register('sw.js')
```

## 4. `build.py` — the whole toolchain

Python 3, **stdlib only** (`json`, `pathlib`, `hashlib`, `re`, `http.server`, `argparse`).

### 4.1 Commands

| Command | Does |
|---|---|
| `python build.py` | inline core into every `tools/*.html` → `dist/`; inject hub tool list; emit `sw.js` + `manifest.webmanifest`; compute + insert per-file CSP |
| `python build.py --check` | all validation gates (§4.4); prints migration burn-down counts; exits non-zero on failure |
| `python build.py --serve` | build + `http.server` on 8000 (PWA mode) |
| `python build.py --new <id>` | scaffold `tools/<id>.html` from a template + append a manifest entry |

### 4.2 Manifest — `manifest/tools.json`

Single source of truth for tool metadata. Strict JSON (ADR D2).

```json
{ "schemaVersion": 2,
  "tools": [{
    "id": "weather",
    "file": "weather.html",
    "name": "Weather Station",
    "cat": "sky",                       // sky|earth|space|civic|money|health|ref|time|local|util|games
    "cx": "M",                          // S | M | L (complexity, from v1)
    "desc": "Current conditions, forecast and details for your saved location.",
    "network": "cors-open",             // offline | cors-open | keyed | relay
    "key": null,                        // or {"name":"nasa","signup":"https://api.nasa.gov","demo":true}
    "endpoints": ["https://api.weather.gov"],
    "storage": ["suite.location", "suite.cache.weather.*"],
    "cacheTtlMin": 10,                  // good-citizen refresh interval (API-AND-RELAY.md §2)
    "since": "v1",
    "flags": []                         // "escape-audit" | "export-missing" | "rate-limited" | …
  }]}
```

Generation targets: hub `TOOLS` array · `sw.js` precache list · `manifest.webmanifest` ·
per-file CSP `connect-src` · CATALOG cross-check · burn-down stats.

### 4.3 Hub generation

`tools/index.html` keeps its v1 chrome, search, pills, and stats logic, but the hand-maintained
71-entry array (v1 `index.html:150–374`) is replaced by a marker the build fills from the manifest:

```js
const TOOLS = /* @suite:tools */[]/* /@suite:tools */;
```

Adding a tool = one manifest entry; the hub, service worker, and CSP all update on next build.

### 4.4 `--check` gates

1. **Manifest ↔ files**: every manifest entry has a `tools/` file and vice versa (hub exempt).
2. **Markers**: every source tool has both `data-suite-inline` tags; hub has the tools marker.
3. **Dist staleness**: rebuilt output hash equals committed `dist/` hash (ADR D9).
4. **No inline handlers**: reject `on\w+=` attributes in dist (kills the v1 `onerror=` pattern —
   v1 `art.html:325`, `books.html:200`).
5. **CSP present** in every dist file; script hashes match actual script contents.
6. **Escaping heuristic**: warn on template-literal interpolation into `.innerHTML` where the
   expression isn't wrapped in `Suite.esc(` (advisory, not fatal — see QUALITY.md §2).
7. **CATALOG cross-check**: warn when a manifest endpoint host doesn't appear in CATALOG.md.
8. **Key hygiene**: fail on anything matching common key patterns in source (except documented
   public demo keys listed in an allowlist).

## 5. `dist/` is committed

So that "clone → double-click" needs no tooling at all (a consumer never runs Python). The build
is deterministic; diffs stay meaningful. Gate §4.4-3 prevents source/dist drift, and the generated
header comment redirects anyone who opens a dist file to the real source.

## 6. localStorage schema & versioning

**All v1 keys are preserved verbatim** — a v1 user's data survives pointing at v2 files unchanged:

| Key | Shape | Notes |
|---|---|---|
| `suite.theme` | `"light" \| "dark"` | absent = follow system |
| `suite.location` | `{lat, lon, label}` | shared across ~20 tools |
| `suite.cache.<tool>.<key>` | `{t: epochMs, v: any}` | the cache envelope; TTL per manifest |
| `suite.key.<name>` | string | user-supplied API keys (nasa, congress, eia, nps, finnhub, ebird, **bart** — new in v2, externalized from v1 `transit.html:163`) |
| `suite.<tool>.*` | tool-specific | e.g. `suite.notes.*`, history lists |

New in v2:

| Key | Purpose |
|---|---|
| `suite.meta.schemaVersion` | int; `Suite.store.migrate()` runs any migrations above the stored version, then bumps it. Baseline v2 = v1 layout, so the migration list **starts empty** |
| `suite.relay.url` | opt-in relay endpoint (API-AND-RELAY.md) |
| `suite.backup.lastExport` | settings.html nags gently when stale |

Caveat (also in PWA.md): `file://` and `http://localhost` are **different origins** with separate
localStorage. The sanctioned bridge is settings.html export/import.

## 7. New tool: `settings.html`

One first-class tool closing three v1 gaps:

1. **Suite-wide backup/restore** — export every `suite.*` key to timestamped JSON; import with
   merge. Fixes the focus.html silent-data-loss class of bug generically (per-tool exports in
   notes/flashcards stay, for interop formats).
2. **API key manager** — UI over `suite.key.*` with signup links from the manifest.
3. **Relay config** — set `suite.relay.url` + a connection test button.

Plus: theme, location editor, storage usage viewer, per-tool cache purge.

## 8. Decision records (ADR table)

| # | Decision | Alternatives rejected | Why |
|---|---|---|---|
| D1 | Generator = **Python stdlib, single `build.py`** | Node script; make; no generator | v1 docs already assume Python (`python -m http.server`); zero install; stdlib covers inlining, hashing, serving. Node drags a runtime the philosophy never references |
| D2 | Manifest = **strict JSON** | YAML; JS module | stdlib-parseable from Python and (if ever wanted) the browser; no dependency; comments belong in CATALOG.md anyway |
| D3 | Templating = **external refs in source, inlined at build** (`data-suite-inline`) | body-fragment + wrapper template; runtime injection | source files stay valid double-clickable HTML → no watch mode, no rebuild loop while developing; dist honors the contract |
| D4 | PWA = **protocol-gated SW registration** | separate PWA build; always-on SW | one `if (location.protocol.startsWith('http'))`; file:// behavior untouched, PWA purely additive |
| D5 | CORS-blocked sources: **embed monthly data at build time (BLS) + link-out cards for live data (airport, custom transit)**; relay exists only as an optional power-user template | default shared relay; per-user relay setup; keep `.example` placeholders | simplest thing that meets *just works and easily sharable*: zero infrastructure, zero setup, nothing to maintain or pay for. CORS only restricts browsers, so `build.py --refresh-data` fetches BLS server-side; minute-fresh aviation data is one click away on the source's own site |
| D6 | CSP = **build-generated per-file meta tag with sha256 script hashes** + manifest-derived `connect-src` | no CSP; `unsafe-inline` everywhere | only viable *because* a generator exists; documented fallback: degrade an individual file to `script-src 'unsafe-inline'` if a file:// quirk bites, keeping the `connect-src` allowlist |
| D7 | Backup = **suite-wide export/import in settings.html** | per-tool export code ×71 | one generic dump/restore of `suite.*` beats 71 bespoke implementations |
| D8 | Testing = **static gates in `--check` (with negative tests) + mandatory Playwright smoke suite over all dist files + per-tool verification evidence** | unit tests everywhere; CI server; no automated tests | the failure modes that matter are drift, broken chrome, console errors, and silent regressions — the gate/smoke/evidence stack catches exactly those. Playwright is the one npm concession, isolated in `tests/`, never required to build, always required to ship. No CI server: the executing agent runs the gates and archives outputs; a release with red or unrun gates does not happen |
| D9 | **`dist/` committed**, staleness-checked | dist gitignored | clone-and-double-click for consumers; deterministic build keeps diffs meaningful |

**D6 addendum — CSP verdict (Phase 1, 2026-07-15).** The generated hash-based CSP was tested on
all three pilots (focus, weather, hub) opened from `file://` in Chrome 138+, Edge 138+ (real
installed browsers) and Firefox (Gecko 151): scripts execute under the sha256 hashes, live
`connect-src` fetches succeed, `img-src` radar imagery loads, **zero CSP violations, zero console
errors** across all 9 browser×file combinations (evidence:
`tests/evidence/phase1/csp-verdict.txt`). **Verdict: full hash-based CSP ships suite-wide in
Phase 2; the per-file `unsafe-inline` fallback remains documented but was not needed.**

**D6 addendum 2 (Batch B, 2026-07-15).** One tool needed a narrower per-file relaxation than the
documented fallback: geo.html's Census geocoder is JSONP-only by the provider's design (no ACAO
header — re-verified via curl and a live fetch probe). The manifest entry may declare
`scriptEndpoints`: hosts appended to that file's `script-src` alongside the hashes. Scripts still
cannot be injected from anywhere else, and no file uses `unsafe-inline`. Sole user: geo.html →
`https://geocoding.geo.census.gov`.

## 9. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Editing dist by accident / forgetting to rebuild | staleness gate (§4.4-3) + generated header comment + "never edit dist" in every doc |
| Manifest vs CATALOG drift | build cross-check warnings; crisp role split (machine truth vs prose + verification dates) |
| CSP hash brittleness across browsers from `file://` | pilot on 3 tools in Phase 1 **before** suite-wide rollout; per-file fallback documented (D6) |
| SW staleness masking updates | content-hash cache names + `skipWaiting`/`clients.claim` policy in PWA.md |
| Quality drift across 71 parallel migrations | batches grouped by risk class so shared defects surface early; one subagent per tool with the orchestrator reviewing every diff against `v1-import`; per-tool evidence directories; burn-down table cross-checked by `--check` |
| Home-directory git hazard (`C:\Users\henry` is a repo — anything outside a real repo silently belongs to it) | Phase 0's first task: `git init` here and verify `git rev-parse --show-toplevel` resolves to this folder |
| `file://` vs localhost storage split | documented in PWA.md; settings.html export/import is the bridge |
